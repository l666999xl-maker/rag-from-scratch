## 一、先判断：这份数据适不适合 BM25

BM25 的强项是**精确词匹配**。这份书恰好有一大批很"实"的词：

```
桶装水   葡萄柚   安全带   赔偿金   身份证   失业保险金
```

用户很可能直接问"桶装水和自来水哪个贵""葡萄柚能不能和降压药一起吃"。
这些问题里出现了原文的原词，BM25 会非常准。

它也有明确的弱项：

```
用户问："不想上班了怎么办"
原文写："离职""被裁""辞职"
```

问法和原文用词对不上时，BM25 就数不到词。这不用现在解决——第 5 课的向量检索专门补这一块。
**这一课先把基线建起来：用词对得上时，BM25 必须又准又快。**

## 二、先理解三件事

### 1. BM25 只做一件事：数词，再加权

对每个"问题词 × 每个块"：

```
分数 = Σ  该词在这块出现的次数 × 该词有多稀有 × 长度惩罚
```

| 量 | 含义 | 这本书里的例子 |
|---|---|---|
| **TF** | 词在本块出现几次 | "桶装水"在第 5 节第 14 条里出现 4 次 |
| **IDF** | 词在多少块里出现过 | "的"几乎每块都有 → 权重接近 0；"葡萄柚"只在少数块出现 → 权重很高 |
| **长度惩罚** | 长块因为字多，容易"蒙中"词 | 防止 2000 字的块仅靠篇幅压过 300 字的块 |

`rank_bm25` 的 `BM25Okapi` 把这三样都算好了。你要做的是**喂给它正确的分词结果**。

### 2. 中文必须分词

英文有空格，`text.split()` 就能切词。中文不行：

```python
"医保报销比例".split()   # ['医保报销比例']  一个"词"
```

如果不分词，整句话变成一个 token。而语料里几乎没有哪一块恰好包含这 7 个连续的字，
于是 TF 永远是 0，BM25 完全失效。

jieba 切完：

```python
jieba.lcut_for_search("医保报销比例")
# ['医保', '报销', '比例']
```

**分词不是优化项，是中文 BM25 的前提。**

### 3. 索引只建一次

建索引 = 把 1017 块全部分词、统计词频、算 IDF。
这份数据要 2.2 秒。如果每次查询都重建，交互模式每问一句卡 2 秒。

所以结构是：

```
启动 → load_index() 建一次 → 之后每次 search() 只用
```

## 三、动手：代码怎么读

打开 `src/bm25_search.py`，按顺序看四个部分。

### 1. `tokenize`：把文本变成词列表

```python
def tokenize(text: str) -> list[str]:
    tokens = []
    for token in jieba.lcut_for_search(text.lower()):
        token = token.strip()
        if not token or token in STOPWORDS:
            continue
        if not MEANINGFUL_RE.search(token):
            continue
        tokens.append(token)
    return tokens
```

四个决定，每个都有原因：

| 写法 | 为什么 |
|---|---|
| `lcut_for_search` | 长词会额外切出子词。"桶装水"同时给出 `桶装`、`桶装水`，查询只写"桶装"也能命中 |
| `.lower()` | 书里有 `NHTSA`、`BMI`、`HR`、`CUP`，统一小写，`Bmi` 和 `BMI` 才能算同一个词 |
| 过滤标点 | `MEANINGFUL_RE` 要求 token 里至少有一个汉字/字母/数字，纯标点丢掉 |
| 少量停用词 | 只删"的、了、是、在"这类虚词。**别贪多**："不""没""要"在问句里有含义 |

分词结果可以直接看到：

```
查询：桶装水比自来水贵多少
分词：桶装 / 桶装水 / 比 / 自来 / 自来水 / 贵 / 多少
```

数字和百分号也能保留：

```
"2.67 倍"    → ['2.67', '倍']
"45% 死亡风险" → ['45%', '死亡', '风险']
```

这意味着用户拿原文里的数字来搜，也能命中。

### 2. `BM25Index`：建索引

```python
class BM25Index:
    def __init__(self, chunks):
        self.chunks = chunks
        self.corpus = [tokenize(chunk["text"]) for chunk in chunks]
        self.bm25 = BM25Okapi(self.corpus)
```

注意传入的是**每块的分词列表**，不是原始文本：

```python
BM25Okapi([["桶装", "桶装水", "贵"], ["保险", "报销"], ...])
```

`chunk["text"]` 里已经包含第 3 课加的 `【节名】` 和条目标题，所以节名、标题、正文都会被检索到。
`refs` 不参与索引——这是第 3 课把参考文献移出正文的直接收益：网址不会变成一堆 `https`、`www` 噪声词。

### 3. `search`：打分、排序、去重

```python
scores = self.bm25.get_scores(query_tokens)
order = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)
```

`scores` 的长度等于块数，每个值是该块和问题的相关性。然后从高到低取前 k 个。

**但这里有一个这份数据特有的坑：一条建议可能被切成多块。**

第 3 课里 138 条超长建议被拆成 2–3 块，每块都重复标题。
如果不去重，top-5 会被同一条建议占满。实测：

```
查询：失眠先吃药还是先做认知行为治疗
不去重：[(3,26), (6,34), (3,26), (29,14), (6,34)]   ← 3-26 和 6-34 各出现两次
去重：  [(3,26), (6,34), (29,14), (2,13), (4,13)]
```

所以 `search` 里加了去重：

```python
key = (item["kind"], item.get("section_no"), item.get("item_no")) \
    if item["kind"] == "tip" else item["id"]
if key in seen:
    continue
```

对"条"来说，`(节号, 条号)` 相同就是同一条，只保留分数最高的那一块。
前言、导语、附录本来就一块一个 id，按 `id` 去重即可。

### 4. 打分只到 0 就不返回

```python
if scores[i] <= 0:
    break
```

一个查询词都没匹配上的块，分数是 0。把它返回给用户没有意义，还会把 prompt 撑长。

## 六、四个实验（必须动手）

### 实验 1：不分词会怎样

把 `tokenize` 临时改成：

```python
def tokenize(text: str) -> list[str]:
    return text.split()
```

重跑 6 条基准问题。

**实测结果：Top-1 命中 0 / 6。**

原因：中文没有空格，整句话变成一个 token，语料里没有任何一块包含完全相同的长串。
这个实验就是"中文必须分词"的证明。改完记得改回来。

### 实验 2：`lcut` 和 `lcut_for_search` 的区别

把 `tokenize` 里的 `lcut_for_search` 换成 `lcut`，重跑 6 条。

**实测结果：这 6 条仍然是 6 / 6。** 因为这些问题的词都很短，两种切法够用。

那为什么要用 `lcut_for_search`？找一个长词试试：

```
"失业保险金"  → lcut_for_search 会同时给出 "失业""保险""失业保险金"…
```

查询词被切得更细，召回面更大。代价是 token 变多、索引变大。
**在这份数据上，先用 `lcut_for_search`，等第 8 课有评测数字再决定要不要换。**

### 实验 3：关闭去重

把 `search` 的 `dedupe` 默认值改成 `False`，重跑"失眠"那条。

**实测：top-5 里 `(3,26)` 和 `(6,34)` 各出现两次，实际只看到 3 条不同建议。**

去重不是可选项——只要你的切块允许一条建议拆成多块，检索结果就必须按条去重。

### 实验 4：top_k 取多少

把 `DEFAULT_TOP_K` 改成 3 / 5 / 10，观察：

- k=3：第 7 课塞给模型的上下文更短、更省 token，但可能漏掉正确的第 4 条
- k=10：召回更全，但噪声更多，模型更容易被无关内容带偏

**先保留 5。** 第 8 课用 Recall@k 和回答质量来定这个数，而不是凭感觉。

## 七、BM25 的边界（这一课要亲眼看到）

跑这两条：

```powershell
.\.venv\Scripts\python.exe src\bm25_search.py "怎么少花冤枉钱"
.\.venv\Scripts\python.exe src\bm25_search.py "不想上班想辞职"
```

第一条的 Top-1 是第 5 节的导语（intro），不是某一条具体建议；
第二条的前两名里也混着导语。

原因很简单：**BM25 不认识"冤枉钱"和"浪费钱"是同一个意思，它只数词。**
导语里恰好出现了这些字，于是分数高。

这不是 bug，是关键词检索的天花板。第 5 课的向量检索会用语义相似度补这一块；
第 6 课的混合检索把两路结果融合；第 8 课的评测会告诉你到底补上了多少。

## 八、这一课的设计决定（面试会问）

| 决定 | 原因 |
|---|---|
| 索引 `text`，不索引 `refs` | 第 3 课已经把网址移出正文，避免 `https`、`www` 污染词表 |
| 用 `lcut_for_search` | 长词切子词，提高中文召回 |
| 英文统一小写 | `NHTSA` / `BMI` / `HR` 在书里大小写混用 |
| 保留数字和百分号 | 用户会拿"2.67 倍""45%"来搜 |
| 停用词只删虚词 | 删"不""没""要"会改变问句含义 |
| 按 `(节号, 条号)` 去重 | 一条建议可能被切成多块，不能占满 top-k |
| 分数 ≤ 0 不返回 | 零匹配的块只会增加噪声和 token 成本 |
| 索引只建一次 | 2.2 秒建索引 vs 1 毫秒查询 |
