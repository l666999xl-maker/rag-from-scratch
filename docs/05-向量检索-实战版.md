## 一、先理解三件事

### 1. Embedding 把"意思"变成向量

```
"葡萄柚和降压药能一起吃吗"
    → [0.021, -0.044, 0.073, ...]   1024 个数字

"西柚会让降压药在血里升到几倍"
    → [0.019, -0.041, 0.070, ...]   数值很接近——意思相近

"今天天气不错"
    → [-0.51, 0.033, -0.12, ...]    数值差很远——意思无关
```

这 1024 个数字没有人类可读的含义。不要试图解释"第 37 维代表什么"，
你只需要知道：**意思相近的文本，向量方向也相近。**

这正好补上 BM25 的短板：

```
BM25：  问"药和水果能不能一起吃"  → 找不到，因为原文写的是"葡萄柚"
向量：  问"药和水果能不能一起吃"  → 找得到，因为"水果"和"葡萄柚"语义相近
```

### 2. 余弦相似度：只看方向，不看长度

两个向量的夹角越小，越相似：

```
方向一致   → 余弦接近 1   → 很相似
方向垂直   → 余弦接近 0   → 无关
方向相反   → 余弦接近 -1  → 意思相反
```

为什么不看距离？因为向量长度常常和文本长短相关。
我们不希望"一段 1400 字的长块"仅仅因为长就被判定为不相似。

**实现技巧**：先把所有向量归一化（长度变成 1），余弦相似度就等价于点积：

```python
scores = self.normalized @ query_vec
```

这一行一次算出"查询"和全部 1017 个块的相似度。

### 3. 为什么不每次重建

把 1017 个块送进 embedding 接口要 **30 秒、51 次请求**。
每次查询都重建，交互模式每问一句卡 30 秒。

所以：

```
第一次运行 → 向量化 1017 块 → 存 build/embeddings.npy
之后每次启动 → 直接读 .npy（读文件本身不到 0.1 秒；整个进程启动约 1.3 秒）
每次查询 → 只向量化用户那一句话（1 次请求）
```

## 二、动手：代码怎么读

打开 `src/vector_search.py`。

### 1. `embed_texts`：分批调用接口

```python
BATCH_SIZE = 20

for start in range(0, len(texts), BATCH_SIZE):
    batch = texts[start:start + BATCH_SIZE]
    response = client.embeddings.create(model=EMBEDDING_MODEL, input=batch)
    vectors.extend(item.embedding for item in sorted(response.data, key=lambda x: x.index))
```

- 百炼兼容接口单批最多 **20 条**，所以 1017 块要发 51 次
- 按 `item.index` 排序再 `extend`，保证向量顺序和块顺序严格一致
- `dtype=np.float32`：1024 维 × 1017 块，float32 约 4 MB，float64 要 8 MB

### 2. 缓存 + 指纹：什么时候必须重建

```python
def chunks_fingerprint(raw: bytes) -> str:
    return hashlib.sha256(raw).hexdigest()[:16]
```

`build/embeddings_meta.json` 里存三样：

```json
{
 "model": "qwen3.7-text-embedding-flash",
 "count": 1017,
 "dim": 1024,
 "fingerprint": "a1b2c3d4e5f60708"
}
```

启动时只有四个条件全满足才读缓存：

1. 不是 `--rebuild`
2. `embeddings.npy` 存在
3. **模型名一样**
4. **chunks.json 的指纹一样**

任何一条不满足，就自动重建。

**这是这一课最重要的工程细节。**
换 embedding 模型、或者改了第 3 课的切块参数，旧向量和新向量就不在同一个空间里。
检索**不会报错**，只会安静地变差——分数整体变低、结果变得莫名其妙。
指纹 + 模型名就是用来防止这种"安静的 bug"的。

### 3. `VectorIndex`：归一化

```python
norms = np.linalg.norm(vectors, axis=1, keepdims=True)
norms[norms == 0] = 1.0
self.normalized = vectors / norms
```

`norm(..., axis=1, keepdims=True)` 的形状是 `(1017, 1)`，可以直接和 `(1017, 1024)` 广播相除。
`norms[norms == 0] = 1.0` 防止除零——虽然正常 embedding 不会出现零向量。

查询向量也要归一化一次：

```python
norm = np.linalg.norm(query_vec) or 1.0
query_vec = query_vec / norm
```

### 4. 打分和去重

```python
scores = self.normalized @ query_vec
order = np.argsort(-scores)
```

`np.argsort(-scores)` 是"升序排负数"，等价于"降序排原分数"。

去重逻辑和 BM25 完全一样：

```python
key = (item["kind"], item.get("section_no"), item.get("item_no")) \
    if item["kind"] == "tip" else item["id"]
```

因为第 3 课把 138 条长建议拆成了 2–3 块，不去重的话 top-5 会被同一条建议占满。

### 5. 入口

```powershell
# 第一次：建索引（30 秒）
.\.venv\Scripts\python.exe src\vector_search.py --rebuild "葡萄柚和降压药能一起吃吗"

# 之后：读缓存 + 查询
.\.venv\Scripts\python.exe src\vector_search.py "葡萄柚和降压药能一起吃吗"

# 缓存坏了或想强制重建
.\.venv\Scripts\python.exe src\vector_search.py --rebuild
```

不要拿向量分数和 BM25 分数直接比：BM25 是 51.1，向量是 0.748，两个尺子完全不同。

## 四、和 BM25 做同题对照（这一课的重点）

用第 4 课的 6 条基准问题，再加 6 条"换个说法"的问题，两个系统各取 Top-3。

### 词汇重合的 6 条

| 问题 | 标准答案 | BM25 Top-1 | 向量 Top-1 |
|---|---|---|---|
| 桶装水比自来水贵多少 | 5-14 | 5-14 | 5-14 |
| 被公司裁了赔偿金怎么算 | 19-6 | **19-6** | 19-4 |
| 葡萄柚和降压药能一起吃吗 | 34-13 | 34-13 | 34-13 |
| 失眠先吃药还是先做认知行为治疗 | 3-26 | 3-26 | 3-26 |
| 身份证丢了怎么补办 | 7-11 | 7-11 | 7-11 |
| 坐后排要不要系安全带 | 1-1 | 1-1 | 1-1 |

**BM25 6/6，向量 5/6（Top-3 都是 6/6）。**

向量输的那条很典型：问题里精确出现了"赔偿金"，BM25 直接锁定第 19 节第 6 条
（"违法解除的，赔偿金是经济补偿标准的二倍"）；向量则把第 19 节第 4 条
（"被裁先算清 N"）排在了前面——两条都在讲裁员赔偿，语义上确实接近。

### 换个说法的 6 条

| 问题 | 标准答案 | BM25 Top-1 | 向量 Top-1 |
|---|---|---|---|
| 喝酒吃头孢会怎么样 | 34-11 | 34-11 | 34-11 |
| 想辞职又不想亏了补偿 | 19-7 | 19-7 | 19-7 |
| 老人摔倒了要不要马上扶 | 13-2 | 13-2 | 13-2 |
| 怎么看屏幕不伤眼睛 | 6-16 | 6-16 | 6-16 |
| 孩子怎么预防近视 | 30-4 | 30-6 | **30-4** |
| 通宵之后怎么补觉 | 2-38 | 2-38 | 2-38 |

**BM25 5/6，向量 6/6（Top-3 都是 6/6）。**

这组问题还不够"换个说法"——"头孢""辞职""摔倒""近视"这些词原文里都有，
所以 BM25 依然很强。真正能看出向量价值的是下面两条。

### 两条没有共同关键词的问题

| 问题 | BM25 Top-1 | 向量 Top-1 | 标准答案 |
|---|---|---|---|
| 药和水果能不能一起吃 | 2-27（不对） | **34-13** | 34-13 葡萄柚 |
| 喝酒之后吃消炎药有事吗 | 16-10（不对） | **34-11** | 34-11 头孢 + 酒 |

这两条是向量检索存在的理由：

- "水果"和"葡萄柚"没有字面重合
- "消炎药"和"头孢"没有字面重合

BM25 数不到词，向量能理解它们说的是同一类东西。

### 结论

| 场景 | 谁更强 |
|---|---|
| 精确词、专有名词、数字、法条名 | **BM25** |
| 口语问法、同义改写、上位词（水果 → 葡萄柚） | **向量** |
| 两者都强、但排序不同 | 混合检索（第 6 课） |

**不要现在就宣布"向量更好"或"BM25 更好"。**
它们在**不同的题上**各赢一半，这正是第 6 课要做 RRF 融合的原因。

## 六、四个实验（必须动手）

### 实验 1：`BATCH_SIZE` 改成 1

```python
BATCH_SIZE = 1
```

删掉 `build/embeddings.npy` 和 `build/embeddings_meta.json`，重新 `--rebuild`，计时。

**预期**：1017 次请求，耗时从 30 秒涨到十几分钟（还容易触发限流）。
改回 20。

**要体会**：批量不是"优化"，是"能不能在合理时间跑完"的问题。

### 实验 2：去掉归一化

把 `VectorIndex.__init__` 里的归一化删掉，直接用原始向量做点积：

```python
self.normalized = vectors
```

重跑同样的问题。

**预期**：长块的分数会明显偏高，排序变差。
原因：没归一化时，点积同时受"方向相似"和"向量长度"影响，
而向量长度往往和文本长度相关。

改完记得改回来。

### 实验 3：缓存什么时候失效

1. 先跑一次查询，记下启动时间（读缓存，很快）
2. 把 `src/chunk_text.py` 的 `MAX_CHUNK_CHARS` 从 1000 改成 1500，重跑第 3 课
3. 再跑 `vector_search.py`

**预期**：它不会报错，而是自动重新向量化。
因为 `chunks.json` 的指纹变了。

**这是这一课最该记住的工程细节**：切块变了，向量必须重建；
只换模型不重建，检索会安静地变差。

## 七、已知限制

1. **向量不懂精确词权重**：问"赔偿金"，它可能给你"经济补偿""N+1"这些同义条目，
   但不一定把原文写着"赔偿金"的那条排第一。这正是 BM25 的强项。
2. **主题相近 ≠ 答案正确**：问"被裁了怎么算钱"，向量的前几名都在这一个主题里，
   但具体条目可能不是你要的那条。所以 Top-1 不能盲信，Top-3 更稳。
3. **长块会稀释**：第 3 课已经把参考文献移出正文，否则 1000 多字的块里一半是网址，
   向量会被拉偏。这是切块质量直接影响检索的又一个例子。
4. **每次查询要调一次接口**：约 0.3–0.4 秒，离线或接口故障时不可用。
   BM25 是纯本地的，1 毫秒。
5. **成本**：1017 块 × 约 700 字，一次建库约 50 万 token 量级（具体看计费口径）。
   所以必须缓存，不能每次启动重建。

## 八、下一步

第 6 课混合检索：

```
BM25 排名  +  向量排名  →  RRF 按名次融合  →  最终 Top-K
```

为什么按名次而不是分数？因为 BM25 的 51.1 和向量的 0.748 没有可比性。
RRF 只用"排第几"这一个信息，天然避开分数尺度问题。

到时候用今天这 12 条问题验收：
目标不是某一路 12/12，而是**两路的强项都保住**。
