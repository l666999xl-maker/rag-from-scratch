## 一、重排（rerank）是什么

前面三路的排序依据各不相同：

- BM25：数词
- 向量：语义相似度
- 混合：两路的名次（RRF）

它们都没有真正"读"过问题和候选原文放在一起的样子。
重排模型就是把「问题 + 一条候选」成对送进去，输出一个相关性分数。

```
用户问题
   ↓
混合检索取 CANDIDATES = 20 条候选
   ↓
重排模型给每条候选打分（读原文，慢但准）
   ↓
按新分数取前 5 条
```

**为什么放在最后**：重排每对都要算一次，20 条候选就是 20 次计算。
如果对全部 1017 块做重排，一次查询要几十秒。先用便宜的检索把范围缩小，再用贵的模型精排，
这是检索系统里最常见的一层结构。

### 接口

DashScope 的重排不走 OpenAI 兼容格式：

```
POST https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank
{
  "model": "qwen3.7-text-rerank",
  "input": {"query": "...", "documents": ["候选1", "候选2", ...]},
  "parameters": {"return_documents": false, "top_n": 20}
}
```

实测注意两点：

1. `/compatible-mode/v1/reranks` 返回 **404**，必须用上面这个原生端点。
2. 响应里的 `output.results` 是 `[{"index": 3, "relevance_score": 0.92}, ...]`，
   **`index` 是候选列表里的下标**，要按它把分数映射回原来的顺序。

代码用标准库 `urllib` 发这个请求，所以没有新增任何依赖。

### 失败要能退回去

重排是一次外部调用，会超时、会限流。检索不该因为它挂掉：

```python
try:
    scores = rerank(query, [hit["text"] for hit in hits])
except (urllib.error.URLError, KeyError, ValueError, TimeoutError) as exc:
    print(f"[警告] 重排失败，退回混合检索排序：{type(exc).__name__}")
    return hits[:k]
```

**降级路径要显式写出来**，不要指望"接口不会挂"。

### 实测代价

| | 混合检索 | 加重排 |
|---|---|---|
| 单次查询 | 约 0.4 秒 | 约 1.1 秒 |
| 接口调用 | 1 次 embedding | 1 次 embedding + 1 次 rerank |
| 排序依据 | 两路名次 | 问题与原文的直接相关性 |

## 二、评测集升级

### 从 30 条到 50 条，并且分成两半

第 8 课的 30 条问题已经被用来调过混合检索的权重（1:3）和评分规则，
严格来说它们已经"见过"了。所以这一课：

- 原来的 30 条标成 `dev`：随便用来调参、改 prompt
- 新增 20 条标成 `holdout`：**不参与调参**，只在最后报告成绩

| | dev | holdout | 合计 |
|---|---|---|---|
| 资料内 `in` | 20 | 12 | 32 |
| 部分覆盖 `partial` | 4 | 6 | 10 |
| 资料外 `out` | 6 | 2 | 8 |

新增的 20 条覆盖了睡眠、开会、失业保险金、枪支认定、离婚冷静期、
接单红线、食品广告、心肺复苏、租房押金、退役安置、母乳喂养、对乙酰氨基酚等条目。

**为什么要分**：如果所有题都参与调参，你报出来的分数是"背过的题"的分数。
holdout 掉分才是真实水平——这一课你就会看到 dev 1.90、holdout 1.58。

### 新增两个指标

`Recall` 只问"前 3 条里有没有正确答案"，不关心排第几。
RAG 很在意第 1 名，所以补两个排序敏感的指标：

```
MRR@3  = 平均( 1 / 第一个正确答案的名次 )     没命中算 0
nDCG@3 = DCG / IDCG
         DCG  = Σ  rel_i / log2(i + 1)        i 是名次，rel 是 0 或 1
         IDCG = 理想排序下的 DCG
```

用大白话说：

- **MRR**：正确答案排第 1 得 1 分，排第 2 得 0.5 分，排第 3 得 0.33 分
- **nDCG**：把所有可接受答案都排到最前面才算 1.0。
  像 `in-02` 有两个可接受条目（19-6 和 19-4），两个都靠前才拿满分

## 三、结果

### 1. 检索指标（四路对比）

**dev（资料内 20 条）**

| 方法 | R@1 | R@3 | MRR@3 | nDCG@3 |
|---|---|---|---|---|
| BM25 | 80% | 100% | 0.892 | 0.900 |
| 向量 | 100% | 100% | 1.000 | 1.000 |
| 混合 | 100% | 100% | 1.000 | **0.996** |
| **重排** | 100% | 100% | 1.000 | **1.000** |

**holdout（资料内 12 条）**

| 方法 | R@1 | R@3 | MRR@3 | nDCG@3 |
|---|---|---|---|---|
| BM25 | 92% | 100% | 0.958 | 0.969 |
| 向量 | 100% | 100% | 1.000 | 1.000 |
| 混合 | 100% | 100% | 1.000 | 1.000 |
| 重排 | 100% | 100% | 1.000 | 1.000 |

怎么读：

1. **BM25 依旧是短板**。dev 上 R@1 只有 80%，四条没中第 1 名（预防近视、痛风尿酸、手机丢失、彩礼返还）；
   holdout 上 12 条里错 1 条（开会那条）。R@3 都是 100%，说明它"能找到，但排不准"。
2. **向量在这份语料上非常强**，两组的 R@1、MRR、nDCG 全是满分。
3. **混合没有超过向量**，而且 dev 的 nDCG 还低了 0.004——
   因为 `in-02` 有两个可接受条目，混合把 19-4 排到了第 2 名之后。
4. **重排把这点差距补上了**：召回没变（都是 100%），nDCG 从 0.996 回到 1.000。
   **重排改的是顺序，不是召回。**

### 一个必须诚实说的结论

在这份语料上，重排的收益**很小**：只体现在 dev 的 nDCG 上（0.996 → 1.000），
其他所有格子都一样。

原因还是那句老话：这本书的条目写得很具体，检索本身就不难，
候选前 20 里几乎总包含正确答案，重排只是在微调顺序。

重排真正值钱的场景是：语料大、同主题条目多、候选里有大量"像但不是"的干扰项。
那时候它会把第 7、8 名拉上来。**要知道它在你的语料上值不值，就得像这样量一次。**

### 2. 回答行为

| | dev | holdout | 合计 |
|---|---|---|---|
| 资料内未误拒 | 20/20 | 12/12 | **32/32** |
| 资料外正确拒答 | 6/6 | 2/2 | **8/8** |
| 部分覆盖处理对 | 4/4 | 6/6 | **10/10** |
| 引用编号有效 | 22/22 | 18/18 | **40/40** |
| 接口拦截 | 0 | 0 | 0 |

### 3. LLM 评分

| | 题数 | 平均分 | 完全正确 | 部分正确 | 错误 |
|---|---|---|---|---|---|
| dev | 20 | **1.90** | 18 | 2 | 0 |
| holdout | 12 | **1.58** | 7 | 5 | 0 |

两件事要分开说：

- **dev 从上一版的 1.65 提到了 1.90**。但这一版同时改了重排和 prompt，
  不是控制变量实验，**不能归因到某一个改动**。
- **holdout 的 1.58 才是没见过的题上的真实水平**，比 dev 低 0.32。
  holdout 的问题更细（比如"每晚睡多久最合适"要求同时说出睡得短和睡得长的两个数字），
  也说明 dev 上的高分有一部分来自"题见过"。

7 条部分正确的回答都是漏了关键细节，没有编造：

| 用例 | 漏了什么 |
|---|---|
| dev in-06 | 漏 45%、60% 两个数字 |
| dev in-10 | 漏"眼睛胀痛发红要当急症" |
| h-in-01 | 漏"睡得短高约 12%、睡得长高约 30%" |
| h-in-05 | 漏"法院先调解" |
| h-in-06 | 漏"替诈骗团伙解封账号也有判刑案例" |
| h-in-10 | 三等功的表述有偏差（六种情形之一） |
| h-in-11 | 漏"出生后 1 小时内开奶""6 个月后每天含铁动物性食物" |

### 4. 部分覆盖：从"整段拒答"到"部分回答"

第 7 课的规则 3 只说"先答资料里有的部分"，模型经常干脆整段拒答。
这一版把规则写成了明确的格式：

```
3. 如果资料只回答了一部分：先把资料里有的部分答完，每个结论用 [编号] 标注出处；
   然后另起一行写「资料里没有提到：」再加上缺的那部分。不要因为缺一部分就整段拒答。
```

同时在 `check_answer()` 里加了 `partial` 状态：
既有有效引用、又出现"资料里没有提到"这类句子 → `partial`。

效果（10 条部分覆盖问题）：

| | 按"部分回答"返回 | 仍然整段拒答 |
|---|---|---|
| dev | 2 | 2 |
| holdout | 6 | 0 |
| 合计 | **8** | 2 |

实际输出（`partial-01 深圳医保住院起付线是多少`）：

```
结论：资料里没有深圳医保住院起付线的具体金额。

资料里能查到的相关信息如下：
- 起付线的定义：每次住院时，自己先掏、掏够了医保才开始报的那一段费用 [1]。
- 具体怎么算由各地决定，国办文件没有规定具体算法 [1]。资料给的是四川的例子：
  县中医院起付线为 600 元，转到县人民医院（起付线为 800 元）时，只需再补 200 元 [1]。
- 经基层逐级转诊的参保患者，在上级医院的住院起付线可以连续计算 [1]。

资料里没有提到：深圳医保住院起付线的具体金额、深圳本地的转诊和起付线计算规则。
```

这比"资料里没有提到这个问题"有用得多：用户知道书里讲了什么、缺什么。

dev 里仍有 2 条整段拒答（比特币价格、美国签证材料），
说明 prompt 规则不是万能的——那两条的检索结果和问题距离更远，模型判断不构成"部分覆盖"。

## 四、评测用例本身也会错（这次的真实发现）

跑完第一遍，唯一一条"未通过"是：

```
[holdout out] h-out-02  怎么写一份求职简历
```

去看回答：

```
资料里没有专门讲简历怎么写，只讲了求职的整体方法和求职辅导。[1][2]

资料里与此相关的内容：
- 求职别只投简历，要用系统方法：学技巧、定目标、找人帮。[1]
- 参加过求职辅导的人找到工作的几率，是没参加的人的 2.67 倍 [1]。
...
资料里没有提到：简历的具体写法，包括格式、内容顺序、篇幅、要不要写照片。
```

**这条回答是正确的**：它先说资料里没有简历写法，再给相关条目，最后明确缺口。

问题在**用例标错了**：书里第 5 节第 14 条确实讲了求职方法，
所以这题属于"部分覆盖"，不是"资料外"。把它改成 `h-partial-06`（gold 5-14）后重算：

| | 更正前 | 更正后 |
|---|---|---|
| holdout 资料外拒答 | 2/3 | **2/2** |
| holdout 部分覆盖 | 5/5 | **6/6**（6 条按部分回答） |
| 未通过用例 | 1 条 | **0 条** |

第 8 课讲义里写过一句话：

> 用例写错了，你测出来的是用例的问题，不是系统的问题。

这次又撞上了。而且注意：**改标注之后必须重算统计，并在报告里写清楚改了什么**，
否则你报出去的数字就是错的。

## 五、实验

### 实验 1：重排候选深度

`rerank_search.py` 里的 `CANDIDATES` 决定有多少条候选进入重排。
改大 → 召回更全但更慢；改小 → 快但可能漏掉正确答案。

改成 5 / 10 / 20 / 50，各跑一次 `src/evaluate.py --rerank`，把四个指标记下来：

| CANDIDATES | R@1 | R@3 | MRR@3 | nDCG@3 | 单次查询耗时 |
|---|---|---|---|---|---|
| 5 | | | | | |
| 10 | | | | | |
| **20（当前）** | | | | | |
| 50 | | | | | |

**预期**：R@3 会随候选数上升，超过 20 之后基本不再涨；
耗时几乎线性增长。找到"指标不再涨、耗时还能接受"的那个点。

### 实验 2：关掉重排对比

```powershell
.\.venv\Scripts\python.exe src\evaluate.py
.\.venv\Scripts\python.exe src\evaluate.py --rerank
```

对比两份报告里 `retrieval` 段的 nDCG@3 和 MRR@3。
**预期**：召回一模一样，只有排序指标有微小差别。

### 实验 3：dev 和 holdout 的分数差

同一套参数，dev 1.90、holdout 1.58。
把 holdout 里得分 1 的 5 条打开看，判断是"模型漏了细节"还是"标准答案写得太苛刻"。

改 `gold_answer` 是可以的，但要意识到：**改了标准答案，这一课的历史数字就不可比了。**

### 实验 4：把 rerank 换成"只重排 BM25"

在 `rerank_search.py` 里把 `base` 换成 BM25 索引：

```python
class RerankRetriever:
    def __init__(self, base):   # base 传 bm25_search.BM25Index
```

**预期**：BM25 的 R@3 是 100%，重排应该能把它的 R@1 往上拉。
这是验证"重排能救一路弱检索"的便宜办法。

## 六、已知限制

1. **语料小、条目具体**，所以重排收益小。换到 10 万块的语料上结论可能完全不同。
2. **holdout 只有 20 条**（资料内 12 条），一条对错就是 8 个百分点。
3. **LLM 评分仍有噪声**。`h-in-10` 被判"三等功表述有偏差"，
   可能是模型表述不精确，也可能是评分员过于挑剔。
4. **重排每次查询多 0.7–1.1 秒、多一次计费**。高频场景要算成本。
5. **评测集有来源偏差**：多数问题是从条目标题改写来的，天然偏向"能检索到"。
6. **改正标注后要人工重算统计**，这一步没有自动化，容易漏。
