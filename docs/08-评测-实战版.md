## 一、评测集怎么设计

`data/eval/questions.json` 有 30 条，分三类：

| 类型 | 条数 | 期望行为 | 例子 |
|---|---|---|---|
| `in` | 20 | 正常回答并引用 | 桶装水比自来水贵多少 |
| `partial` | 4 | 拒答，或说明资料只覆盖一部分 | 深圳医保住院起付线是多少 |
| `out` | 6 | 明确拒答 | 红烧肉怎么做 |

每条的结构：

```json
{
 "id": "in-01",
 "type": "in",
 "question": "桶装水比自来水贵多少",
 "gold_tips": [[5, 14]],
 "gold_answer": "桶装水每升约 1.06 元，北京自来水每升 0.005 元，约是自来水的 210 倍……"
}
```

- `gold_tips`：可接受的检索结果，用 `(节号, 条号)` 表示。
  有些问题有多个可接受条目，比如"被公司裁了赔偿金怎么算"接受 `19-6`（2N）和 `19-4`（N 怎么算）。
- `gold_answer`：给 LLM 评分用的标准答案。**写得短**，只保留关键结论和数字。
- `partial` 的 `expected` 是 `refuse_or_partial`：拒答或明说"资料没有具体数字"都算对。

### 为什么要有 partial 类型

只测"资料内"和"资料外"会漏掉最难的一类：**资料里有相关词，但没有你要的数字**。

比如"深圳医保住院起付线是多少"：
书里第 24 节第 1 条讲了起付线可以连续计算，举了四川的例子，
但没有深圳的具体金额。正确行为不是编一个数，而是说明资料没给。

### 为什么评测集要有区分度

如果 30 条全是"标题原词"查询，BM25 也能 100%，你什么都学不到。
所以这里刻意混了：

- 口语化问法："想辞职又不想亏了补偿"（原文是"不要签个人原因主动辞职"）
- 无共同关键词："药和水果能不能一起吃"（原文是"葡萄柚"）
- 资料外问题
- 部分覆盖问题

## 二、四层指标

### 1. 检索 Recall

只对 `in` 问题算。看标准条的 `(节号, 条号)` 在不在前 1 / 前 3 条里。

```
Recall@1：第 1 条就是标准答案
Recall@3：前 3 条里有标准答案
```

Recall 不关心排第几，只关心"有没有"。

### 2. 回答行为

这是**客观指标**，不需要 LLM 评分：

| 指标 | 定义 |
|---|---|
| 资料内未被误拒 | `in` 问题里，系统正常回答（`status == answered`）的比例 |
| 资料外正确拒答 | `out` 问题里，系统拒答的比例 |
| 部分覆盖处理正确 | `partial` 问题里，拒答或说明只覆盖一部分的比例 |
| 引用编号有效 | 已回答的问题里，`[n]` 都落在本次检索结果范围内的比例 |

### 3. 回答质量

用同一个模型当评分员：

```
2 分：标准答案里的关键结论和数字都答对；可以有多余内容，只要不矛盾
1 分：漏掉至少一个关键结论或数字，或有一处小错误
0 分：主要结论错误、编造关键数字、或答非所问
```

**这是主观指标**，会有波动，只用来看"有没有系统性错误"，不要当成精确分数。

### 4. 为什么不全用 LLM 评分

贵、慢、不稳定。能做成客观指标的就做成客观的：
Recall、拒答与否、引用编号有效，这些都是确定性的。
LLM 评分只用在最后那一层。

## 三、结果与分析

### 1. 检索：BM25 80%，向量/混合 100%

```
BM25   R@1 80%   R@3 100%
       R@1 未中：in-11 孩子怎么预防近视；in-15 痛风的人尿酸要降到多少；
                 in-17 手机丢了先做什么；in-18 彩礼给了还能要回来吗
向量   R@1 100%  R@3 100%
混合   R@1 100%  R@3 100%
```

BM25 的四条 R@1 未中，都在 Top-3 里找回来了，所以 R@3 是 100%。
混合把这四条全部提到第 1 名。

### 一个必须诚实说明的结果

在这套 20 条 `in` 问题上，**向量单独就已经是 R@1 100%**，
混合没有比向量更高。原因有两个：

1. 这本书的条目写得很具体，问题和原文的语义距离本来就不远
2. 评测集的 `gold_tips` 允许"可接受的邻近条目"，比如 19-4 和 19-6 都算对

所以这套评测集能证明"混合不差于单路"，但**不能证明"混合优于向量"**。
要证明后者，需要更难的集合：精确编号、长尾术语、或者故意让语义检索混淆的对照题。
这也是第 6 课权重实验只敢说"14 条问题上的起点"的原因。

### 2. 回答行为：全部通过

```
资料内未被误拒：20/20 (100%)
资料外正确拒答：6/6 (100%)
部分覆盖处理对：4/4 (100%)
引用编号有效：  20/20 (100%)
接口拦截：      0 条
```

这说明第 7 课的三层护栏在这 30 条上是有效的：
该答的答了，该拒的拒了，引用编号没有编造。

### 3. LLM 评分：平均 1.65 / 2

```
完全正确 13 条
部分正确 7 条
错误     0 条
```

7 条部分正确的原因，都是**漏了标准答案里的关键细节**，不是编造：

| 用例 | 漏了什么 |
|---|---|
| in-04 失眠 | 漏"认知行为治疗一般 6 到 8 周" |
| in-06 后排安全带 | 漏"前排致命伤风险降 45%、轻卡降 60%" |
| in-09 老人摔倒 | 只说"按第 13 节第 1 条处理"，没写出"叫不应、没呼吸要做胸外按压" |
| in-10 防蓝光 | 漏"眼睛胀痛发红要当急症" |
| in-12 补觉 | 漏"累计少睡超过 3.5 小时又不补，风险高 42%" |
| in-15 痛风 | 漏"痛风石/骨缺损/每年发作 2 次以上"这个适用条件 |
| in-20 血脂 | 漏"有高血压、高血脂按医嘱规律吃药" |

`in-20` 的评分值得单独说：评分员认为"心脑血管病高危的人每 6 个月查一次"
和"2023 版指南改成按个人需要查"有矛盾，给了 1 分。
从原文看，这是两套口径并列，不算矛盾——**这是 LLM 评分员的噪声**。
所以平均分不能当成精确质量，只能用来发现系统性问题。

### 4. 评分规则会改变结论

第一次评分用的是更严的规则："有多余但不矛盾的内容"也给 1 分。
结果平均分只有 **1.10**，因为模型经常从资料里多写几句正确的细节。

调整成"多余内容只要不矛盾，仍可给 2 分"后，平均分变成 **1.65**。

**同一批回答，两套规则差 0.55 分。**
所以：

- 报告分数时必须同时报告评分规则
- 不要拿不同规则下的分数互相比较
- 想比较两个系统，必须用同一套规则、同一批评测集

## 四、评测抓到的上游 bug（这一课最重要的部分）

写 `in-15` 的标准答案时，我去看第 16 节第 5 条，发现它的标题是：

```
5.68 倍（3.22–10.04），肺癌是 2.17 倍……
```

这明显不是条目标题。继续查，发现真正的第 5 条是：

```
5. 病情稳定的慢性病，在社区医院一次可以开到 12 周的药
```

它被粘在了上一条的正文里。

### 根因

第 3 课的标题正则是：

```python
TIP_START_RE = re.compile(r"^(\d+)\.\s*(.*)$")
```

`\s*` 允许点号后面**没有空格**，于是 `5.68 倍` 被当成"第 5 条"，
而真正的 `5. 病情稳定……` 因为编号已经用掉，没有被识别成新条目。

### 修复

```python
TIP_START_RE = re.compile(r"^(\d+)\.\s+(.*)$")   # 点后必须至少一个空格
```

重跑切块：

```
1015 块 → 1017 块
916 条正文块 → 918
136 条被拆 → 138
```

然后向量缓存因为 `chunks.json` 指纹变了，自动重建（28.5 秒）。

### 这个 bug 的教训

1. **评测不只是测模型，也是测数据。** 写标准答案时要逐条对照原文，最容易发现上游错误。
2. **一个上游小改动会让下游全部失效。** 切块变了，BM25、向量、混合、问答都要重跑。
   第 5 课的缓存指纹就是为这种情况设计的。
3. **数字会变，结论不一定变。** 修复后 14 条对照问题的结果没变，但块数、长度分布都变了。

## 五、怎么运行

```powershell
# 只跑检索，最快（不调 LLM）
.\.venv\Scripts\python.exe src\evaluate.py

# 跑 30 条问答，输出拒答/引用指标
.\.venv\Scripts\python.exe src\evaluate.py --answers

# 再加 LLM 评分
.\.venv\Scripts\python.exe src\evaluate.py --answers --judge

# 只重跑评分，复用上次的回答（改评分规则时用）
.\.venv\Scripts\python.exe src\evaluate.py --judge-only

# 只跑前 5 条，调试用
.\.venv\Scripts\python.exe src\evaluate.py --limit 5

# 问答只取前 3 条资料
.\.venv\Scripts\python.exe src\evaluate.py --answers --top 3
```

报告写到 `build/eval_report.json`，里面保留了每条问题的：

- 检索前 3 条
- 回答状态
- 引用编号
- 模型回答
- 评分和理由

**评测报告要留着**，下次改参数时对比用。

## 六、五个实验（必须动手）

### 实验 1：把混合权重改回 1 : 1

把 `hybrid_search.py` 的 `VECTOR_WEIGHT` 改成 `1.0`，重跑检索。

**实测（20 条资料内问题）**：

| BM25 : 向量 | R@1 | R@3 |
|---|---|---|
| 1 : 1 | 90% | 100% |
| **1 : 3（当前）** | **100%** | 100% |
| 0 : 1（只用向量） | 100% | 100% |
| 1 : 10 | 100% | 100% |

**要体会**：权重不是越大越好；1:1 会丢掉一条语义题，1:3 以上就稳定了。

### 实验 2：加 5 条资料外问题

在 `questions.json` 里加：

```
"怎么申请护照"、"北京地铁几点停运"、"怎么用 Excel 做透视表"、
"这本书的出版社是哪家"、"红烧排骨要炖多久"
```

重跑 `--answers`。

**预期**：拒答率仍然是 100%。如果有一条没拒答，去看它的检索结果——
很可能是检索到了一条"看起来相关"的内容，模型被带偏了。

### 实验 3：把评分规则改回严格版

把 `JUDGE_SYSTEM` 恢复成"有多余内容也给 1 分"，用 `--judge-only` 重跑。

**预期**：平均分从 1.65 掉到 1.10 附近，但"错误"仍然是 0。
**要体会**：分数变化不代表系统变化，先看评分规则。

### 实验 4：`--top 3` 和 `--top 10`

```powershell
.\.venv\Scripts\python.exe src\evaluate.py --answers --top 3
.\.venv\Scripts\python.exe src\evaluate.py --answers --top 10
```

**预期**：`top 3` 时资料内回答可能漏细节，评分下降；
`top 10` 时资料更全，但无关条目也更多，可能引入噪声。
用报告里的 `judge` 和 `answers` 两段对比。

### 实验 5：加 5 条口语化问题

比如：

```
"公司把我开了能拿多少钱"（gold 19-4/19-6）
"吃消炎药能不能喝酒"（gold 34-11）
"孩子老眯眼怎么办"（gold 30-4/30-6）
```

**预期**：BM25 的 R@1 会掉，向量和混合更稳。
如果混合没有提升，检查 `gold_tips` 是不是定得太窄。

## 七、已知限制

1. **评测集只有 30 条，而且是从书里挑的**，不是随机抽样。
   它适合做回归测试，不适合声称"线上准确率 93%"。
2. **`gold_answer` 写得短**，评分员会漏看"回答里的正确补充"。
   调整评分规则可以缓解，但无法完全消除。
3. **LLM 评分有噪声**。`in-20` 就被误判了一次。
   重要结论最好人工抽查。
4. **向量和混合在这套集合上打平**，说明集合的区分度不够。
   要证明混合更好，需要更难的对照题或更大的语料。
5. **只用了 Recall，没有 MRR / nDCG**。Recall 不关心正确答案排第几，
   而 RAG 很在意第 1 名。下一步可以加 MRR。
6. **拒答样本只有 10 条**（6 条资料外 + 4 条部分覆盖），
   拒答率 100% 的置信区间很宽。
7. **评测集会泄漏进开发**。你现在看的这 30 条已经被用来调权重了，
   严格来说应该留一份不参与调参的 holdout 集。
