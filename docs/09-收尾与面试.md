## 一、先写 README

README 不是"给老师交作业"，是**给面试官看的**。
他只会花 30 秒扫一眼，你要让他看到三样东西：**做了什么、多好、怎么验证**。

### 模板

```markdown
# 医院政策问答 RAG

用 6 份真实政策 PDF 构建的问答系统，回答医保、预约、就诊类问题，
并标注每个结论的出处。

## 核心数据

| 指标 | 结果 |
|---|---|
| 检索 Recall@3 | BM25 100% / 向量 92% / 混合 100% |
| 引用有效 | 6/6 |
| 拒答正确 | 2/2 |

## 它是怎么工作的

PDF → 文本 → 切块 → 混合检索（BM25 + 向量 + RRF）→ 拼 prompt → 生成 → 引用校验

## 三个设计判断

1. **为什么要混合检索**：BM25 强在精确词，向量强在语义改写，失败模式不同。
2. **为什么用 RRF 而不是加权**：两路分数量纲不同，没法直接相加。
3. **为什么要有引用校验**：prompt 是软约束，模型可以不听；
   代码校验回答里的来源是否真实存在，才能拦住编造。

## 怎么跑

（三条命令）

## 已知不足

1. 语料只有 6 份，覆盖范围有限。
2. 分块没有处理目录页，也没有做 overlap。
3. 引用校验只能保证"来源没编"，不能保证"结论对"。
4. 没有做 rerank，也没有 query 改写。
```

**注意"已知不足"这一节**。它比"功能介绍"更能体现你想过。

## 二、六个必须能回答的问题

### 1. 为什么要切块？切多大？

> 两个原因：检索精度和成本。整页 800 字塞给模型，它要自己找那一句；
> 切小之后命中的块里大部分是相关内容，token 也省。
>
> 大小没有标准答案，必须实测。我用 500 字，因为政策条款一般一条几十到几百字，
> 500 能装下一到两条；再小会把一条切碎。

### 2. BM25 和向量检索分别擅长什么？

> BM25 看"词出现了没有"，强在精确关键词；向量看"意思像不像"，
> 强在同义改写。
>
> 我的评测集里有一句"每个月工资里扣多少医保"，原文写的是"缴费基数 8%"——
> BM25 很容易漏，向量能找到。反过来搜"爽约"，BM25 更稳。

### 3. RRF 为什么按名次融合？

> 因为两路分数量纲不同。向量是余弦相似度 0~1，BM25 是词频得分 0 到几十，
> 没法直接相加。名次是无量纲的，两路可以比。
>
> 分母加 60 是平滑，避免第 1 名过度主导。

### 4. 模型为什么会编？prompt 为什么拦不住？

> 模型是在预测下一个 token，不是查数据库。不知道答案时它会输出"最像答案"的内容，
> 而且语气一样笃定。
>
> prompt 拦不住是因为它是自然语言，是建议不是规则。
> 我的做法是代码校验：回答里的每个来源，必须真实出现在本次检索结果里，
> 否则降级为兜底话术。

### 5. 你的评测指标是什么？哪个最可信？

> 三个：Recall@3（客观，不调模型）、引用有效率（客观）、拒答正确率（客观）。
>
> 最可信的是 Recall@3 和拒答——它们完全不依赖模型打分，跑一百遍一样。
> 引用有效率依赖模型输出，但判定规则是确定的，只是模型每次写法可能不同。

### 6. 如果继续做，下一步是什么？

> 三件事，按性价比：
> 1. **加 rerank**：现在只有粗排，加交叉编码精排能提升首条命中率。
> 2. **加 query 改写**：用户口语化提问和文档表述差距大时，先让模型改写再检索。
> 3. **扩语料到几十份**：现在的 6 份太少，评测结论只能算方向性。

## 三、3 分钟讲这个项目

按这个结构，掐表练：

> **1. 问题（20 秒）**
> 医院的医保、预约规定分散在很多份 PDF 里，用户查起来很麻烦；
> 更麻烦的是，网上的回答经常给不出出处，你不知道该不该信。
>
> **2. 方案（60 秒）**
> 我用 6 份真实政策 PDF 做了一个问答系统。流程是：
> PDF 提取文本 → 按条款切块 → 混合检索 → 塞进 prompt → 生成 → 校验引用。
>
> 检索用了两路：BM25 和向量，再用 RRF 按名次融合。
> 因为一个强在关键词，一个强在同义改写，失败模式不一样。
>
> **3. 验证（40 秒）**
> 我建了 12 条检索用例和 2 条拒答用例。结果是：
> BM25 Recall@3 100%，向量 92%，混合 100%；引用有效 6/6，拒答 2/2。
>
> **4. 判断（40 秒）**
> 最值得说的是引用校验。一开始我只在 prompt 里写"不要编"，
> 但模型仍然会编一个不存在的文件名当出处。后来加了代码校验：
> 回答里的来源必须真实出现在检索结果里，否则降级。
>
> 另外评测时发现，我最初用的拒答题"你们医院有多少张床位"是无效的——
> 语料里有好几家医院，模型会拿别家的数字答。
> **这不是模型的问题，是用例本身有歧义。**

**第 4 段是重点**。前 3 段任何人都能讲，第 4 段证明你真的做过。

## 四、这份代码的边界（面试主动说）

| 局限 | 说明 |
|---|---|
| 语料只有 6 份 | 覆盖范围有限，结论是方向性的 |
| 没有 rerank | 只有粗排，首条命中还能再提升 |
| 没有 query 改写 | 用户问法和文档表述差距大时会漏 |
| 目录页没过滤 | 第 1 块是目录，会污染检索 |
| 引用校验只查来源 | **不保证结论正确**——这是最需要说清的一条 |
| 没有多轮对话 | 每次问答独立 |
| 单文件、无并发 | 是脚本，不是服务 |

**主动说局限，比被问出来强。**

## 六、面试官可能追问的三个点

**"你的评测集才 12 条，有意义吗？"**

> 统计上不够，我只能说它是方向性的。12 条能发现"某个模块是不是坏了"，
> 但说不了"提升了 5 个百分点"。要下统计结论，至少几百条。

**"引用校验能保证答案对吗？"**

> 不能。它只保证"来源没编"，不保证"结论对"。
> 模型引用了真实文件但理解错了，这层拦不住。要解决得再加一层独立复核。

**"为什么不直接用 LangChain？"**

> 这个项目的目的就是把 RAG 的每一步拆开看清楚。
> 用框架的话，分块、融合、校验都变成黑盒，我讲不清它们内部发生了什么。
> 真实项目里我会用框架，但前提是我知道它在做什么。
